# 缓存容量淘汰核查（2026-10-17，本地 0.36.88）

上轮仅修改了中央图片的内存与磁盘内容缓存，遗漏以下 18 类容量缓存，以及统一元数据总预算的逐项回收路径。本轮均接入 `media/cache-eviction.js` 的 80% 低水位。数量向下取整、至少保留一项；零预算仍不保留。JS Map/Set 和资源释放回调按项执行，一次容量判断选定整批旧项，批内不重新申请预算或重复判定容量。

registry 的 12 类共用同一个实现，同时处理条目数、单所有者字节预算和 TTL；各字节预算继续沿用现有值。超限时先选出整批，移除后统一记账，再执行每项的释放/取消回调。保留替换、过期、清理和销毁的原因与生命周期。版本 token 只清没有引用和在途任务的旧键，别名继续服从现有租约与任务规则。

阅读器被淘汰楼层的解析、页位置图、素材匹配与整楼准备同进同出；保留楼层继续复用准备结果，访问准备结果也更新最近使用顺序。缓存 miss 仍按原读取链重新准备，不修改原正文、素材、存档或用户字段。

TTS 的持久写入与批量删除串行交接，一批删除同时提交，避免多次写入按过期的键列表重复清理。清缓存后递增 epoch，旧请求不回填缓存，新一轮请求的去重身份不被旧任务清除；已经交给播放端的结果不因清缓存而中断。持久缓存继续按写入顺序保留，内存命中更新 LRU。

## 另两处统一处理

- 元数据全局总预算（默认 16 MiB）：之前对其他所有者反复调用单条 `evict`，只清到刚够本次写入。现在一次计算含新数据的总占用，以 12.8 MiB 为目标，按原所有者访问顺序向每个旧所有者请求整批释放。不可分的当前查询和未提供淘汰端口的 CG 视图仍服从硬预算；无法接纳时拒绝缓存，不删除业务记录。成功通过回收接纳的记录不误计为拒绝。
- 提示词关键词编译缓存：原来达到 64 项就整张清空。本轮改为 LRU，超限后保留最近 51 项，命中也更新顺序，避免整张缓存失效后集中重编。

中央图片内容缓存继续批量清至低水位，默认数量 320→256、编码内存 64→51.2 MiB、磁盘 192→153.6 MiB。数量取整也复用统一规则，修正小容量向上取整后仍等于上限的问题。磁盘内容仍通过 `deleteMany` 在一个事务中清理；本轮没有改成单项事务。

## 验证与交付

风险 R3，bundle 同步涉及 R4。新增一个共享低水位 helper，没有新增业务数据库或修改持久业务数据。

相关生成入口回归还发现之前取消历史截断后遗留的 `HISTORY_LOOKBACK` 引用，会让生成开始时的规则注入和复制规则报错。本轮删除两处悬空截断，`history/previousAiTexts` 保留完整非系统历史，标签触发窗口继续独立按原配置选择；没有重新引入固定历史条数。

定向检查覆盖阅读器跨楼淘汰与准备复用、12 类辅助缓存共用的数量/字节/全局预算入口、释放回调与 TTL、资源就绪通知收敛、地图/探测取消、TTS 内存与持久容量、清理期间迟到结果、解码标记和图片内部索引。使用 fake host、测试图片/音频和模拟 provider，未连接真实用户数据。具体执行记录留在本机 `/tmp/igs-reader-cache-20261017/`。真实酒馆、手机和真实 provider 未运行；按用户要求不暂存、提交、推送或打标签。
